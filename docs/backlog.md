## Identity and tenancy (from the E2 spec, later than E2)

- **TOTP MFA and passkeys.** Required before the first paying customer (E2 spec §15, Q3). When it ships, the absolute session lifetime for users without MFA drops from 7 days to 12 h.
- **SAML SSO and SCIM provisioning** for larger agencies.
- **Sessions UI:** list and revoke your own sessions in Settings → Profile.
- **SSE streams re-check the session (spec §6.3, from E2-05).** `GET /campaigns/{id}/events` authenticates when it opens, but a stream that is already open does not notice a logout, an expired session or a deactivated membership. Re-check the session on the keep-alive ping every 60 s (without holding a pooled connection) and close the stream when it has ended; test it in `tests/tenancy/test_sse_tenant` (E2-04's suite). *E2-06:* the same re-check should close the stream when the campaign has left the user's client scope (their client access changed, or the campaign moved to another client); today the scope is checked only when the stream opens.
- **`created_by` and `uploaded_by` in the v2 resources (spec §8.3, from E2-06).** E2-06 records who created a campaign (`campaigns.created_by_user_id`) and who uploaded a resume (`resumes.uploaded_by_user_id`) for signed-in requests (not for the `AUTH_REQUIRED=false` fallback), but `Campaign.created_by` and `Resume.uploaded_by` (`{id, display_name} | null`) are not in the resources yet: they need identity's display names, composed in `app.api.v2` through a port like `ResumeTallies` (one grouped query per list, so the query-count bounds hold). No E2 screen shows them; add them with the first one that does.
- **A new agency starts without a client (E2-06).** The E2-06 migration gave every agency that had no client one named "General", and the seed does the same for its second agency, but an agency created later with `identity.cli create-agency` has none, so its campaigns need a client first (`POST /api/v2/clients`; Settings → Clients from E2-10). Until E2-10 the new-campaign form sends no `client_id` and gets a 422 there. `identity` may not write hiring's `clients` (a leaf module), so a fix is a composed operator step (or accept it once E2-10's form has "New client").
- ✅ **Purge expired sessions (E2-05).** Done in E2-07: `identity.purge_expired` (daily, Celery beat) deletes sessions that ended more than 30 days ago, used or expired reset tokens and invitations expired for 30 days.
- **Password-reset timing (E2-07).** For a known address `POST /auth/password-reset` also deletes the user's unused links, inserts the new one and queues the email: a few milliseconds more than for an unknown address, behind 10 requests per IP an hour. If that ever matters, move the lookup and the token into the task (the request would only count, audit and queue) so both paths do exactly the same work.
- **An existing user with no active agency cannot accept an invitation (found in E2-09).** Accepting as an existing account needs a session (spec §4.3), but `POST /auth/login` answers 403 "no active agency access" without creating one for a user whose memberships are all deactivated (or whose agencies are suspended), and `POST /auth/invitations/accept` without a session is a 409 for an address that has an account. So someone who left one agency cannot join another with the same account. The accept page shows the login's 403. Fix in the backend: let `acceptInvitation` take the password of an existing account (verified with the same limits as login), or let login create a session without an agency when the request carries an invitation token.
- **Problem types for the CSRF and "Choose an agency" 403s (found in E2-09).** Both are `type: about:blank` 403s, so the frontend recognises them by their `detail` text (`CSRF_FAILURE_DETAIL` in `lib/api/csrf.ts`, `CHOOSE_AGENCY_DETAIL` in `lib/api/transport.ts`) to retry with a fresh token or send the user to the agency picker. Give them their own problem `type` URIs (e.g. `/problems/csrf`, `/problems/agency-required`) in `app.platform.csrf` and `identity.dependencies`, list them in the OpenAPI document, and match on the type.
- **A seeded user in two agencies (found in E2-09).** `/select-agency` (a session with several agencies and none active) is unit-tested only: no seeded account has two memberships, so E2E cannot reach it. Add one (e.g. `freelancer@example`, recruiter in both seeded agencies) when E2-10's agency switcher needs it too.
- **The proxy redirect needs one host (E2-09).** `frontend/src/proxy.ts` redirects signed-out page requests to `/login` only when the API is on the page's host, because the session cookie is host-only on the API's host. A deployment that serves the API from another host (`api.` and `app.` subdomains) still works (the auth gate redirects after `GET /me`), but shows a blank page for a moment first. E5 should serve both on one origin (spec §4.1), which also lets the frontend read the CSRF cookie.
- **Undeliverable email (E2-07).** `identity.send_email` gives up after 12 retries (about a day) and logs `email_failed`; nothing tells the inviter, and bounces are not seen at all. Decide with the E5 email provider (bounce webhooks, a "not delivered" state on the invitation).
- **Rate-limiter fail-open (E2-05).** When Redis is unreachable, `app.platform.ratelimit` lets sign-in through and logs `ratelimit_unavailable`. Before E5, decide whether production should fail closed for login instead (an outage of Redis then blocks sign-in), and alert on the log line either way.
