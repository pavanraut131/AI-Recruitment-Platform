## Platform and tooling

- ✅ **Starlette 0.37.2 → current (security, High)**, fixed in S1: FastAPI 0.111.0 → 0.163.1, Starlette 0.37.2 → 1.10.0 (pydantic 2.7.3 → 2.9.2, the minimum FastAPI 0.163 supports). `pip-audit` reports no advisory for Starlette, FastAPI or pydantic any more (it listed 7 for Starlette 0.37.2: GHSA-f96h-pmfr-66vw, GHSA-2c2j-9gv5-cj73, GHSA-86qp-5c8j-p5mr, GHSA-wqp7-x3pw-xc5r, GHSA-x746-7m8f-x49c, GHSA-jp82-jpqv-5vv3, GHSA-82w8-qh3p-5jfq). The upload endpoints (v1 and v2) now parse their body with explicit limits (`app.platform.uploads`: `MAX_FILES_PER_BATCH + 1` files, 10 other fields, 16 KiB per non-file field), and the `PendingDeprecationWarning` about `import multipart` is gone. v1 keeps parsing JSON sent without a Content-Type (`strict_content_type=False` on the root app only).
- **sse-starlette 2.1.0.** Still works on Starlette 1.10 (the SSE snapshots pass), but it is old (3.x is current) and FastAPI 0.135+ has native Server-Sent Events. Decide between upgrading it and FastAPI's own SSE when the v2 stream changes next.
- ✅ **Node 20 → 22.** Done in E1-03 and E1-09: `frontend/Dockerfile`, `Dockerfile.e2e` and both CI jobs use Node 22 (`engines: >=22.22.2`). Node 20 is end of life. Upgrade `frontend/Dockerfile` (`node:20-alpine`) and the `frontend` CI job (`node-version: 20`) together. Best done at the start of E1, before the frontend rebuild.
- **Remove `/api/v1` after E2** (planned as E2-12, [Sprint 8](sprints/sprint-08.md)). The `/api/v1/candidates*` endpoints are a compatibility layer over Applications (spec §7) kept for the current frontend, and `legacy_candidate_map` exists only so old candidate ids keep resolving. Once E1's frontend runs on the new resource API and E2 has shipped, remove the legacy routes, their characterization snapshots and `legacy_candidate_map` (a contract migration, like E0-20).
- **Fake OCR returns placeholder text for tiny PDFs.** A PDF whose text layer yields ≤ 100 characters is treated as scanned (`ingestion.pdf`) and sent to the AI service's OCR. With `AI_PROVIDER=fake`, `FakeAIService.transcribe_page_images` returns a fixed placeholder ("Scanned resume (N page(s), digest …)"), so the profile has no name, email or skills and the resume fails as "not a resume". Real Gemini OCR handles such PDFs; only local smoke tests with very small PDFs are affected (found in E0-20's live check). Fix: make the fake OCR return a deterministic, resume-like text derived from the digest (a name, an email, a few vocabulary skills), so the fake pipeline completes, and update `test_scanned_pdf_falls_back_to_ocr_through_the_ai_service`. Workaround meanwhile: use a test PDF with more than 100 characters of text.
- **Frontend `npm audit` (security, Critical/High).** Found in E1-03, already on `master` (E1-03 adds none and drops `js-yaml`'s). **Partly fixed in S2:** ✅ `next` 16.2.9 (critical: middleware/proxy bypass with Turbopack, Server Actions DoS and SSRF, Image Optimization RCE; `postcss` and `sharp` advisories through it) is fixed by `next` and `eslint-config-next` 16.4.6 (postcss 8.5.23, sharp 0.35.5), and the top-level `postcss` 8.5.15 pinned by `@tailwindcss/postcss` 4.3.1 by refreshing it to 4.3.5 in the lockfile; `npm audit` reports nothing for `next`, `postcss` or `sharp` and no critical. ✅ `axios` ≤ 1.19 and `follow-redirects` through it (high) went with the old UI in E1-10. Still open (E1-10: 1 high, 10 moderate, none in a runtime dependency of the app): dev-only tooling (high/moderate: `picomatch`, `brace-expansion`, `minimatch` and `fast-glob` through `eslint-config-next`/`typescript-eslint`, `vitest`/`vite`, and the `shadcn` CLI with `ts-morph`/`@dotenvx/dotenvx`). Before anything is exposed publicly (E5), and ideally during E1.
- **Pitch screenshots from curated data (Sprint 6 retro).** The README's screenshots come from the E2E run, so the campaign title and emails carry the run id ("E2E mwn8tnclkzft Python platform"). Take them from a curated demo dataset (a seed profile, or a screenshot-only run with friendly names) before pitching.
- **Make `e2e` a required check (E1-09).** The job arrived with E1-09 and is not in the branch protection rule yet. Add it (CONTRIBUTING.md, step 4) once it has been green on `master` for a few runs.
- **E2E: more than the hero flow (E1-09).** **Partly done in E1-10:** the hero flow now goes on to the campaign's Insights, Talent (with search) and Home, with axe and screenshots, and follows an old `/candidates/<id>` link to `?open=`. Still only unit-tested: a failing upload and "Retry failed", bulk move/reject, J/K/S on the table, editing a campaign in Settings.
- **Merged legacy candidate ids in v2 (E1-10).** Old `/candidates/<id>` links now open the application through `getApplication`, but `GET /api/v2/applications/{id}` looks up the application's own id only, while v1 also follows `legacy_candidate_map` (candidates merged into an application during E0). A link to a merged candidate therefore shows "Candidate not found". If old links matter (they predate any customer), let the v2 lookup follow the map too, or add a small `GET /api/v2/legacy-candidates/{id}` that answers with the application's id.
- **E2E flakiness on a long-lived local stack (E1-10).** On Windows with Docker Desktop, repeating the suite many times against one kept stack (`E2E_KEEP=1`, `--repeat-each=10`) failed half the repeats at random steps: requests that never reached the API (a POST after its preflight), a stylesheet that never loaded. Fresh stacks (`make e2e`, CI) pass. If it shows up in normal use, check whether it's the port forwarding (try `127.0.0.1` instead of `localhost` for the base and API URLs) before touching the tests.
- **Backend suite: dropped Postgres connections on Windows (E2-01).** The full `pytest` run on this Windows / Docker Desktop host fails a few tests with `server closed the connection unexpectedly` or `WinError 64`. They are always the ones that open many connections at once: the 20-worker `test_resolve_person_concurrency` tests, and once `test_the_list_queries_use_the_indexes`. `master` at E1-10 does the same (5 of 748 failed in one run), and the tests pass when run on their own and in CI. It looks like the Docker Desktop port proxy that `tests/postgres.py` already describes, now under load. If it gets in the way, try fewer concurrent connections in those tests, or a retry on connect in their engine, before suspecting the code.
- **E2E job speed (E1-09).** The `e2e` job builds the backend (apt packages, `uv sync`) and frontend (`npm ci`, `next build`) images from scratch on every run. If it gets slow, cache the layers between runs (buildx with the GitHub Actions cache, e.g. `docker buildx bake` over the Compose files with `cache-from`/`cache-to: type=gha`) rather than trimming the test.
- **Contrast of translucent tints (E1-09).** `npm run check:contrast` checks token pairs, not a token at 10 % over another surface: the E2E's axe run found the table's required-skill chips (teal text on `bg-primary/10` over an active row) at 4.44:1, fixed by giving them foreground text. The review panel's skill chips keep teal on `bg-primary/10` over the plain background (about 4.6:1, passing but close). Either add the tinted pairs (`primary` on `primary/10` over `background`, `muted` and row states) to the contrast script, or give chips an opaque tint token.
- **Request bodies with server defaults are required in the generated client.** `openapi-typescript` treats a property with a `default` as always present (right for responses: pydantic leaves defaulted fields out of `required`, but they are always sent), so `CampaignCreate.status` and `required_skills` are required in `POST /campaigns`'s TypeScript body (ADR 0006). Harmless (the form sends both) but surprising. Fix when it bites: list response fields with defaults as required in the v2 document (pydantic's `json_schema_serialization_defaults_required` on the v2 response models, with an OpenAPI snapshot update), then generate with `--default-non-nullable false`.
- **Campaign list sort (E1-04).** `GET /api/v2/campaigns` lists newest first only. The list shows "last activity", and recruiters will want the most recently active campaigns on top: add a `sort` parameter (`-last_activity_at`, `-created_at`, `title`), as `listCampaignApplications` has, then make the column sortable in `features/campaigns`.
- **Breadcrumbs show `#id` for a campaign (E1-04).** `components/app-shell/breadcrumbs.tsx` derives labels from the URL, so `/campaigns/[id]` reads "Campaigns › #1a2b3c4d". Let a page set its segment's label (a small context in the app shell that the workspace fills with the campaign title) rather than having the shell fetch data.
- **Shared empty and error states (E1-04, E1-05).** `EmptyState` and `ErrorState` live in `features/campaigns/components/data-states.tsx`, so that E1-05, built in parallel, would not collide on a shared file. Once both have merged, keep one pair in `src/components` and use it in both features (E1-05's `NoCandidates`, `NoMatches`, `EmptyPage` and `LoadError` in `features/applications/states.tsx` become thin wrappers over it).
- **Typed `score_breakdown` and profile entries (E1-07).** `Application.score_breakdown` and the Person's `profile.education` / `work_experience` / `projects` are open objects in the v2 document (`Record<string, never>` in TypeScript), so the frontend reads them defensively (`scoreParts`, `features/people/model.ts`) and hard-codes the sub-score maxima (40/30/15/10/5) from the scoring prompt. The data is also inconsistent: the extraction prompt writes `work_experience[].role`, the seed writes `title`. Declare pydantic models (`ScoreBreakdown`, `WorkExperience`, `Education`, `Project`; maxima in the document or a `score_parts` list), normalise `title`/`role`, regenerate the client.
- **Phone on the application's person (E1-07).** `Application.person` is `{id, name, email}`, so the review panel shows the email only; the phone needs the Person (`GET /people/{id}`, which the panel loads for "Also applied to" anyway). Add `phone` to `PersonRef` if the panel should show it without that request.
- **Lost updates on notes (E1-07; more pressing once E2 adds several users per agency).** `PATCH /applications/{id}` has no concurrency check: two tabs (or two recruiters, after E2) editing the same notes overwrite each other silently. Add an `ETag` / `If-Match` (or `updated_at` precondition, 412 on mismatch) and let the autosave show a conflict instead of overwriting.
- ✅ **`features/campaigns` on the shared data states (E1-07).** Done in E1-08: `features/campaigns` uses `src/components/data-states.tsx` and its copy is deleted. Still open: the applications table's `states.tsx` (and the Uploads tab's `LoadError`, below) could wrap the shared pair.
- **Breadcrumbs show `#id` for a Person (E1-07).** Same as the campaign item above: `/people/[id]` reads "People › #55341abb". The same page-label context would fix both.
- **Fixture view panel saves fail (E1-07).** `/dev/candidates` now renders the full review panel over synthetic rows that are not in the API, so its "Also applied to" and saves fail against a real backend (by design: it measures the table). If the panel itself needs a dev playground, give the fixture view a fake API or seed the Query cache.
- **Applications list sorts (E1-05).** `GET /api/v2/campaigns/{id}/applications` has no `-name` (Z→A) and no sort by experience, category or stage, so the table sorts name A→Z only and leaves those columns unsortable. Add the sort values in the hiring service, with contract snapshots and a regenerated client.
- **"Unreviewed" stage filter (E1-05).** An application with no stage (`pipeline_stage` is `null`) can't be selected by the `stage` filter, though the Insights counts report it. Add an `unreviewed` filter value (not a stage) and offer it in the toolbar.
- **Expose `Content-Disposition` through CORS (E1-05).** The export's file name is set by the server, but the browser can't read the header cross-origin, so the table builds its own name. Add `expose_headers=["Content-Disposition"]` to the CORS middleware (it disappears anyway once the frontend is same-origin in E5).
- **"Select all matching" across pages (E1-05).** Bulk actions and export take ids only (1–500), so a selection covers the current page (≤100 rows). Add a filter-based variant (`{action, filters}`) for bulk actions, with a confirmation that shows the count.
- **"Only processing / failed" toggle (spec §5.1, E1-05).** Not built: the applications list has no resume-status filter, and an application exists only once a resume is scored. Decide with E1-06 (Uploads) whether this belongs in the table or only in the Uploads tab.
- ✅ **"S" focuses the stage selector (spec §5.1).** Done in E1-07: in the review panel and on the Person profile.
- **Branch protection on `master`** requires the five CI checks. The `backend-test` job now also runs the coverage gate (E0-21); no new check name, so nothing to change in the rule.
- **Upload limits are not in the API (E1-06).** `MAX_FILE_SIZE_MB` and `MAX_FILES_PER_BATCH` are settings, but no endpoint or OpenAPI constraint exposes them, so `frontend/src/features/uploads/limits.ts` copies the defaults (and the rejection wording) by hand; a deployment that overrides them gets client checks that disagree with the server (the server still decides). Expose them, e.g. `GET /api/v2/config` (or `maxItems` / a documented limit on `Body_uploadResumes`), and read them in the Uploads tab.
- **No event when a resume starts its AI step (E1-06).** The worker sets `processing` without publishing, and `ResumeEvent` has no `processing_step` or `retry_count`, so the Uploads tab shows a resume as Extracting until it is done (Analysing appears only after a refetch). Publish `processing` (and each step change) with `processing_step`; the cache patch in `useCampaignEvents` then shows it with no frontend change beyond copying the step.
- **Quota rows have no retry time (E1-06).** A `quota_exceeded` resume carries only the message; the Uploads tab assumes the Gemini free tier's reset (midnight Pacific, `features/uploads/quota.ts`), and the worker's own automatic retry (`quota_retry_delay`) is invisible. Add `next_retry_at` (or `retry_after`) to `Resume` and the event.
- **Retry is campaign-wide only (E1-06).** `retryFailedResumes` re-queues every failed and quota-limited resume, so the tab offers one "Retry failed" for the campaign rather than a Retry per row (spec §5.3). Add `POST /api/v2/resumes/{id}/retry`. The retry also publishes no event (rows reset to `pending` silently), so the tab patches them itself; publish `pending` for each retried resume.
- **Uploads: cancel and persistence (E1-06).** Queued or uploading batches cannot be cancelled (add an abort to `postUpload` and a Cancel on the row). Client-side rejections live in the tab's state and go when it unmounts; finished batches are forgotten 30 minutes after the tab stops showing them (mutation `gcTime`).
- **Uploads has a third load-error block (E1-06).** `features/uploads/uploads-tab.tsx` has its own `LoadError`; fold it into the shared empty/error states above.
- **No event stream across campaigns (E1-08).** Each workspace streams its own campaign's events, so Home (`features/home`) refetches `GET /home` every 5 s while resumes are processing (and not at all otherwise). Add a workspace-wide stream (e.g. `GET /api/v2/events`, the same `resume_update` events with their `campaign_id`; per agency after E2) and let Home invalidate `home` from it, as the workspace does.
- **`Home` doesn't say whether any campaign exists (E1-08).** When it has no active campaigns, nothing processing and no strong matches, Home calls `GET /stats` to tell a first run ("Create your first campaign") from campaigns that are all closed or archived. Add `campaigns_total` (or the status counts) to `Home` and drop the second request.
- **Required-skill coverage in the campaign stats (E1-08).** `CampaignStats.top_skills` lists the 10 most common skills only, so Insights can say a required skill is "not among the most common" but not how many applicants have it. Add `required_skills: [{skill, count}]` (every required skill, count 0 included) and show them all in the Top skills chart.
- **Talent sorting (E1-08).** `GET /api/v2/people` sorts by most recently updated only. Add a `sort` (`name`, `-application_count`, `-last_applied_at`) and make the Talent columns sortable (E6 replaces the search itself).

## Identity and tenancy (from the E2 spec, later than E2)

- **TOTP MFA and passkeys.** Required before the first paying customer (E2 spec §15, Q3). When it ships, the absolute session lifetime for users without MFA drops from 7 days to 12 h.
- **SAML SSO and SCIM provisioning** for larger agencies.
- **Sessions UI:** list and revoke your own sessions in Settings → Profile.
- **Breached-password check** at sign-up and password change (k-anonymity range API).
- **Joining by email domain** ("anyone signing in with @agency.com joins as a recruiter"), E2 spec §15, Q6.
- **Move old storage keys.** E2-03 writes new objects under `agencies/{agency_id}/…`, and older objects keep their stored paths. A script can copy them to the new layout and update `resumes.file_path`.
- **Per-prefix bucket policies** in E5, so a leaked app credential is limited to one agency's prefix.
